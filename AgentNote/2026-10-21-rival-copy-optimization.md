# 競合の航路開設時の退避コピー縮小

2026-10-21。比較元は4.1.6 `f6f6e61086b3da6ee41f6e87abcf6968901861ff`。ローカル実装・検証のみ。版番号、保存形式、ゲームルールは変更しない。GitHub・Sitesへの反映なし。

## 実装と変更範囲の監査

`apply_rival_candidate`の`Game`全体のCloneを、対象会社と共通の`next_id`の退避に置き換えた。処理順は免許購入→必要なら商館建設→航路開設で維持し、既存と同じ`Result::Err`で復元する。対象会社の復元には資金、破産状態、帳簿、累計、免許、初回免許による友好度変更、商館、船、経路と運行設定などの全フィールドを含む。

| 呼出し | 書き込む状態 |
|---|---|
| `buy_license` | 対象会社の入出金・帳簿・免許・初回免許フラグ・友好度 |
| `build_post` | 対象会社の商館・入出金・帳簿 |
| `open` | 対象会社の経路、共通`next_id` |
| `buy_ship` | 対象会社の船・入出金・帳簿、共通`next_id` |
| `assign`／`reschedule` | 対象会社の船の割当・待機状態、経路の周期基準日・荷役率・監視状態 |
| 上記からの照会 | 船種、価格、航続距離、接続表、道路状態を読むだけ |

市場・道路・都市投資・他会社・世界イベント・乱数・設計一覧は変更しない。Engineの接続表、描画キャッシュ、日次船団、並列実行の状態にも書き込まない。今後これらの下位処理に副作用を追加する場合は、この専用トランザクションの境界を再監査することをコードに記載した。汎用の全ゲーム操作に使う仕組みではない。

## 失敗時の検証方針

Rustテストには4.1.6の全Game退避方式を比較用に残し、同じ候補・初期状態から旧方式と新方式を実行する。対象会社だけでなくGame全体のJSONを比較する。

- 1つ目の免許購入後に、重複免許／2つ目の資金不足で失敗。
- 免許購入後、既存商館への重複建設で失敗。
- 商館建設後、無効な船種／目的国の免許不足／船購入資金不足で失敗。
- 有効な50航路を保有し、新規航路は拒否、既存航路への増船は成功。
- 新造船、未使用船の再利用、既存航路への増船が成功する場合も、全GameとID増分が一致。
- 実際の購入・割当まで完了した後に、テスト用のコールバックから意図的にErrを返し、採番を含む完全復元を確認する。この最後のケースは将来の遅い失敗を想定した故障注入であり、実在する正常入力の開設失敗を装っていない。本番の失敗フックは追加していない。

## 性能結果

AMD Ryzen AI 5 PRO 340、Node v24.15.0。以下は通常設定の平均日次計算時間（ms／ゲーム内1日）、各360日×3試行。起動・描画・保存の時間は含まない。

| 条件 | 4.1.6 | 変更後 | 平均時間の短縮 |
|---|---:|---:|---:|
| 600隻 | 2.320 | 1.731 | 25.4% |
| 2,400隻 | 3.528 | 3.048 | 13.6% |
| 600隻・倉庫即時調整あり | 2.598 | 2.510 | 3.4% |
| 2,400隻・倉庫即時調整あり | 3.951 | 3.740 | 5.3% |
| 提供セーブ（1408日目） | 5.412 | 4.889 | 9.7% |

逐次固定／強制4スレッドでも同じ5条件を比較した。

| 条件 | 逐次固定・変更前→後 | 強制4スレッド・変更前→後 |
|---|---:|---:|
| 600隻 | 2.322→2.184 | 3.130→2.779 |
| 2,400隻 | 3.512→3.118 | 4.430→3.999 |
| 600隻・倉庫即時調整あり | 2.648→2.369 | 3.590→3.244 |
| 2,400隻・倉庫即時調整あり | 4.009→3.841 | 5.104→4.750 |
| 提供セーブ | 5.473→4.768 | 7.071→6.563 |

全90試行で最終保存ハッシュが一致し、保存再読込も一致。計算ジョブのJSメッセージは0のまま。[生の測定結果](2026-10-21-rival-copy-benchmark.json)に各試行・ハッシュ・計測条件を保存した。

測定にはばらつきがある。600隻の変更後通常設定は1.541～2.055 ms／日で、逐次固定の短縮は約5.9%に留まるため、25.4%を常に得られる改善率とは扱わない。倉庫あり600隻の通常設定は変更前後の範囲が重なり、3.4%の差は小さい。各試行のp95の平均は同条件で2.926→3.060 ms、提供セーブで5.696→5.858 msとなり、全指標が改善したわけではない。今回確認したのはこのCPU・データでの日次計算の平均時間であり、画面FPSの改善率ではない。強制並列は引き続き逐次より遅く、並列化自体の効果とこのコピー削減の効果を混同しない。
