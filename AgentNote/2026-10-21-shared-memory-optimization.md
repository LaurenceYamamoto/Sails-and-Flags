# 共有メモリ移行後の性能分析と最適化

2026-10-21。直前の共有メモリ実装を変更前として比較する。版番号4.1.3は維持し、GitHub・Sitesには反映しない。テストはローカルのみ。

## 原因の切り分け

1. **削除した転送は、旧方式でも常時発生していたわけではない。** 4.1.3の自動選択は、並列化が遅い仕事を既に逐次へ戻していた。したがって、JSON転送を廃止した分だけ全日次処理が一律に速くなる比較ではなかった。
2. **共有メモリの割当・解放には同期がある。** 使用中の固定nightlyの`library/std/src/sys/alloc/wasm.rs`を確認した。atomics有効時は、Systemのalloc/dealloc/reallocが共通のロックを取得する。共有版の逐次実行にもこの費用があり、並列中には競合し得る。ロックそのものを削除する危険な対応は行わない。
3. **高頻度の成功処理が不要な割当をしていた。** `Engine::spec`は`ok_or("船種が不正です。".into())`のため、船種が見つかる正常時にもエラー文字列を作って破棄していた。運行周期・危険度・維持費などから反復して呼ばれる。共有メモリではこの無駄にも上記のロックが伴う。
4. **同じ結果の再計算・コピーが多かった。** 同じ船種の船の数だけ航程・荷役時間を再計算し、経路の出発時差を船ごとにVecへコピーしていた。危険度キャッシュも、キャッシュヒット時まで船種名をStringへ複製していた。
5. **独立カーネルが短い。** 較正で毎回プールを起こして比較すると、並列化しないと決めるためにも同期費用を払う。さらに小さな仕事にも128回ごとの比較を繰り返していた。

NodeのCPUプロファイルも採取した。2,400隻、720日、共有版の逐次固定、初期化と保存を計時外とした診断で、変更前は`spec`の自己サンプルが13.7%、`__rdl_dealloc`が10.1%、`__rdl_alloc`が5.1%を占めた。これはホットスポットの根拠であり、全体の遅延をこの比率だけで因果分解した値ではない。インライン化・サンプリングの影響があるため、関数名がプロファイルから消えたことを「その費用が完全にゼロになった」とは扱わない。mutex競合の待機時間そのものの直接計測も行っていない。

## 実装

- 正常な船種検索ではエラー文字列を確保しない。入力検証の同種の即時文字列生成も遅延化し、エラー内容は維持。
- 運行周期は経路に存在する船種ごとに計算。船団の順序は変えず、重複する同型船の計算だけ省く。共有計算では船団索引を借用し、Vecの余分なコピーを行わない。
- 出発時差は日次の経路ごとに1配列を保持し、船はその配列の索引を持つ。保存形式には影響しない。
- 危険度キャッシュのキーは船種名を借用する。会社・船の一意なキーの並べ替えは追加バッファ不要のソートにする。順序は同じ。
- 生産適性に使う都市の基礎生産量の最大値を、品目ごとに全品目から探す代わりに都市ごとに一度計算する。演算式と集計対象は同じ。
- Rustの自動選択では、逐次計測が0.1ms未満なら並列比較を省略。再計測は軽量な仕事で1024回、それ以外で256回、または仕事量が2倍になったとき。十分大きい仕事の並列比較と30%の採用余裕、劣化時の逐次復帰は維持。
- 新たな外部ライブラリ・ゲームルール変更・セーブ移行はない。

単一のマイクロ修正だけでなく上記の一組を評価しているため、最終速度差のすべてを`ok_or_else`だけの効果とは断定しない。

## 再現方法

変更前の`assets/wasm/shared`を編集前に`sites/shared-optimization-before`へコピーし、同時にshared-build.jsonと通常版WASMも保存した。これは公開用成果物ではなく、Git管理外のローカル比較資料。比較スクリプトは変更前の生成JS・Worker・WASM一式を実際に読み込む。

`npm run benchmark:shared-optimization`で、同じ初期状態から30日ウォームアップし、リセット後の360日×3試行を測定する。各方式を独立プロセスで起動し、実行順を回転。起動・描画・保存は計時外で、日次準備・較正・同期・確定を含む。最終保存ハッシュの全方式一致と、共有版の日次JSジョブメッセージ数0を必須にする。

- 既定: 60経路×10隻。
- `BENCH_SHIPS_PER_ROUTE=40`: 2,400隻。
- `BENCH_SAVE`: 提供された1408日目セーブを読み取り専用で使用。
- `BENCH_MODES`で方式、`BENCH_DAYS`・`BENCH_TRIALS`で期間・試行数を変更可能。

CPUプロファイルは`WASM_PROFILE=1`で共有ビルドし、`CPU_PROFILE`に出力先を指定して`node scripts/benchmark-shared-optimization.mjs --mode profile/serial`を実行する。プロファイル用ビルドはシンボルを保持し、`sites/shared-profile`へ出力する。`scripts/summarize-cpu-profile.mjs`で関数別の自己サンプルを集計できる。性能表はプロファイラーを使用しない通常ビルドで別に測定する。

## 残る制約

状態確定・資金予約・乱数順序を逐次で扱う部分、文字列や帳簿の割当、共有アロケーターの同期は残る。スレッド数を増やせば必ず速くなるとはしない。今後の判断は自動選択を含む全体時間で行う。

## 最終比較結果

AMD Ryzen AI 5 PRO 340、Node 24.15.0。各条件360日×3試行の平均（ms/ゲーム内日、低いほど速い）。比較元は直前ターンの共有メモリ版であり、4.1.3公開版そのものではない。変更前バイナリのSHA-256 `03de557ff662502c481e58bf1e8424d98d588f2127e1a140bb56c9342128017f`が前回の最終成果物と一致すること、Workerを含む変更前パッケージ全体が保存済みマニフェストと一致することも確認した。

| 条件 | 600隻 | 2,400隻 | 提供セーブ |
|---|---:|---:|---:|
| 変更前・自動選択 | 4.095 | 7.146 | 8.027 |
| 変更後・自動選択（通常設定） | 2.971 | 5.567 | 6.481 |
| 通常設定の時間短縮率 | **27.4%** | **22.1%** | **19.3%** |
| 変更前・逐次固定 | 3.529 | 6.902 | 8.177 |
| 変更後・逐次固定 | 2.952 | 5.359 | 6.460 |
| 変更前・4スレッド強制 | 5.918 | 13.387 | 11.633 |
| 変更後・4スレッド強制 | 3.836 | 6.609 | 8.216 |

強制4スレッドは約35.2%、50.6%、29.4%短縮したが、変更後の自動選択よりはなお遅い。今回の成功は不要な割当・再計算・較正の削減であり、「並列実行が逐次実行を上回った」とは報告しない。

全54試行で、各初期状態からの最終保存データが変更前後・各実行方式で完全一致し、再読込後も一致。日次JSジョブメッセージは0。提供セーブは読み取りのみで変更していない。[全試行の時間・p95・最大値・保存とバイナリのハッシュ](2026-10-21-shared-optimization-benchmark.json)。

プロファイラーなしの比較を、ビルドや自動テストと同時実行せずに測定した。前回記録は180日、今回は360日のため、前回の絶対時間とこの表を直接比較しない。数値はこのCPUとNode上の結果であり、すべての端末・ブラウザで同じ率になる保証ではない。

[CPUプロファイルの集計](2026-10-21-shared-optimization-profile.json)も保存した。720日の診断実行でも最終保存ハッシュは完全一致。プロファイル付きの時間は上表に混ぜていない。
